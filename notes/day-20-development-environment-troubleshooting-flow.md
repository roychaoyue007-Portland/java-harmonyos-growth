## 2. 为什么不能只说“报错了”

“报错了”只是结果现象，不是原因。

排错时要把现象记录清楚：

```text
我执行了什么命令
我在什么目录执行
完整错误信息是什么
错误出现在哪一步
是命令找不到、路径找不到、配置错误、端口问题，还是程序运行失败
```

完整错误信息通常包含错误原因、报错位置、关键路径、命令名、异常类型或日志线索。它是排查入口，不是附属内容。

## 3. 综合排错的层次

本地项目跑不起来或访问不了，可能发生在不同层次：

| 层次 | 可能问题 | 检查方向 |
| --- | --- | --- |
| 命令层 | 命令不存在、命令拼错 | `Get-Command`、完整错误信息 |
| 路径层 | 当前目录不对、文件路径不存在 | `Get-Location`、`Test-Path` |
| 环境变量层 | PATH、JAVA_HOME 未配置或配置错误 | `$env:PATH`、`$env:JAVA_HOME` |
| 配置层 | 端口、日志路径、文件路径、运行模式、访问路径配置错误 | 配置文件、启动参数 |
| 进程层 | 程序没有启动、启动后退出 | `Get-Process`、任务管理器 |
| 端口层 | 服务没有监听目标端口、端口被占用 | `Get-NetTCPConnection -State Listen` |
| 访问层 | localhost、端口、路径写错 | 浏览器地址、`Test-NetConnection` |
| 日志层 | 错误上下文和失败原因 | 控制台输出、启动日志、错误日志 |

## 4. 配置文件可能影响什么

配置文件不只影响服务端口。

它可能影响：

```text
具体端口
日志路径
启动模式
文件路径
运行模式
访问路径
服务对应的功能
依赖配置
```

所以，如果命令能执行、工具能运行、进程也启动了，但访问仍然失败，就要检查配置文件中的端口、路径、模式和功能开关。

## 5. 进程存在和端口监听的区别

进程存在：说明程序已经启动成一个正在运行的进程。

端口监听：说明服务进程打开了某个端口，正在等待客户端连接请求。

需要修正一个表达：

```text
服务不是“特殊的静态进程”。
服务是适合长期在后台运行的程序；服务启动后会成为正在运行的进程。
```

也要注意：

```text
服务启动不一定代表目标端口监听成功。
端口监听正常也不代表访问路径一定正确。
```

## 6. 日志的作用

日志记录程序运行过程、错误上下文和失败原因，帮助我们看到错误发生前后发生了什么。

日志能解决：

```text
只看到“失败了”，但不知道失败前发生了什么
只看到最后一行错误，但不知道前面哪一步触发
需要确认程序是否启动、加载了什么配置、监听了哪个端口、在哪一步退出
```

日志不是最后才看的装饰品，而是定位原因的重要证据。

## 7. 原因假设和验证

原因假设是根据错误信息、日志和当前观察结果，提出一个“可能原因”。

它不是确定结论。

例如：

```text
现象：localhost:8080 访问失败
证据：8080 没有监听，3000 正在监听
原因假设：服务可能配置成了 3000 端口
验证：查看配置文件或访问 localhost:3000
```

排错要从“猜”走向“验证”。
